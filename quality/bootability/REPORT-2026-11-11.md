## 2. A 层 · 逐代码补丁审计

工具：`patch_audit.py`　结果：`records/patch-audit.json`

### 2.1 总览

- 逐字节 diff：**9 处差异区段 / 480 字节**
- 写入跳转：**16 条**（`b` / `bl`）
- **归属覆盖 9/9**（全部映射到具体 hook 组，来源 `hooks[]`，引擎声明 19 个区间）
- **全部 4 字节对齐**（`align4=True`）
- **全部跳转目标落在 Image 内**（`0 ≤ target < 0x2100000`）
- 0 项阻断级发现

### 2.2 每处改动落在哪个函数（这是"逐代码检查"的核心产出）

| 偏移 | 长度 | hook 组 | 所在符号 | 跳转 |
|---|---|---|---|---|
| `0x00024bd4` | 180 | `do_execve` | `die` | 3 条 `b` |
| `0x001c1720` | 4 | `audit_log_start` | `audit_log_start` | 1 条 `b` |
| `0x0028f130` | 12 | `cfi_bypass` | `report_cfi_failure` | — |
| `0x0038fcd4` | 4 | `do_execve` | `do_execveat_common` | 1 条 `b` |
| `0x003a1d88` | 4 | `filldir64` | `filldir64` | 1 条 `b` |
| `0x003a276c` | 4 | `compat_filldir` | `compat_filldir` | 1 条 `b` |
| `0x005e1830` | 4 | `avc_denied` | `avc_denied` | 1 条 `b` |
| `0x0085dee8` | 120 | `drm_puts_coredump` | `__drm_puts_coredump` | 4 条 `b` |
| `0x0085dfbc` | 148 | `drm_printfn_coredump` | `__drm_printfn_coredump` | 4 条（含 `bl`） |

### 2.3 两个需要解释的点（不是缺陷，但必须说清）

**(a) 两处 code cave 落在 `__drm_*_coredump` 里，而这两个符号被我的分类器标记为「驱动」。**

这是引擎 **>= 6.1 分支的设计**：该分支要求 `die` + `__drm_puts_coredump` +
`__drm_printfn_coredump` 三个符号同时存在，把这两个 coredump 函数的空余空间当作
跳板存储区（`engine/src/patch_pipeline.cpp:133-171`）。它们名字里带 `drm_`，但实际
是**内核崩溃转储的辅助函数**，不是显示驱动 —— 真正的 DRM 显示栈是 `drm_atomic_*` /
`msm_*` / `mipi_*` 那一族，本次**一处都没被碰**。

为避免这条被当成静默豁免，`driver_integrity.py` 里把它写成**显式白名单**
`DRM_COREDUMP_EXCEPTIONS`，并在报告中保留 `is_driver=True` 的标记供人工复核 ——
即「标记但豁免」，不是「看不见」。

**(b) `report_cfi_failure` 的 `inside_symbol=False`。**

引擎日志里该符号只有地址没有 size（`report_cfi_failure:28f130`），所以无法断言
「改动在其范围内」。这是**已知的观测缺口**，不是失败：该处 12 字节改动本身通过了
对齐与跳转检查。要闭合这个缺口，需要该符号的 size（`System.map` 或真机 kallsyms）。

## 3. B 层 · 驱动完整性

工具：`driver_integrity.py`　结果：`records/driver-integrity.json`

| 指标 | 值 |
|---|---|
| 符号名解码 | **119,907** 个 |
| 驱动相关符号 | **8,103** 个 |
| 地址映射来源 | 引擎符号解析日志（23 个符号带地址） |
| 引擎声明触碰的符号 | （旧版 report 未导出 hooks 明细，见 §6 局限） |
| **落在驱动符号内的改动** | **0**（除两个已解释的 coredump cave） |

**符号是怎么解出来的**：这是本层能成立的关键。裸 Image 没有 ELF 节表，
但本样本内核把符号名以**未压缩的 NUL 分隔字符串**存放（在 `0x18ca534` 附近可见
`…\x00do_execveat_common\x00__register_binfmt\x00…`）。`common.load_kallsyms()`
用「最长标识符字符/NUL 连续窗口」定位该 blob，解出 11.99 万个名字。

**地址从哪来**：裸 Image 的符号**地址数组**布局是版本相关的（项目 C++ 分析器各自实现），
我没有在 Python 里重猜一遍——猜错会产生**错的符号映射**，比没有更糟。改为解析引擎
自己解析出的地址（`sym:ADDR, size:SIZE`），因为引擎为了 patch **必须**先解对地址。
两者交叉使用：名字来自镜像，地址来自引擎，再用 diff 的偏移做最终核对。

> 若 `--engine-log` 缺失，DI-3 会**明确报 gap**（`warnings` 里写明
> 「已跳过，非通过」），而不是静默 PASS —— 这条本身有负样本 `NEG-DI-mapping-gap`。

## 4. C 层 · 开机行为验证（qemu）

工具：`boot_qemu.py`　结果：`records/boot-qemu.json` + 原始串口日志

qemu 参数（两者**完全相同**，这是判据成立的前提）：

```
-M virt -cpu cortex-a57 -m 2048 -kernel <Image> -nographic -serial mon:stdio \
-no-reboot -append "console=ttyAMA0 earlycon=pl011,0x9000000 ignore_loglevel loglevel=7 panic=1"
```

### 4.1 逐层结果

| 层 | 原厂 | patched | 判读 |
|---|---|---|---|
| L1 可加载 | ✔ | ✔ | qemu 接受镜像，未报 invalid image |
| L2 早期启动 | ✔ | ✔ | 串口输出 `Booting Linux` / `Linux version` / `bootconsole` / `earlycon` |
| L3 用户态 | ✘ | ✘ | 两者均未进入用户态 |
| **启动深度** | `rootfs-mount-attempted` | `rootfs-mount-attempted` | **完全相同** |

### 4.2 内核实际跑到哪一步（这是最有价值的部分）

原厂与 patched 的串口日志**在内容上完全一致**（290 行），停在同一处：

```
[    0.554621] No soundcards found.
[    0.559278] uart-pl011 9000000.pl011: no DMA platform data
[    0.566474] /dev/root: Can't open blockdev
[    0.566808] VFS: Cannot open root device "(null)" or unknown-block(0,0): error -6
[    0.567007] Please append a correct "root=" boot option; here are the available partitions:
[    0.571744] Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)
[    0.572241] CPU: 0 PID: 1 Comm: swapper/0 Not tainted 6.1.25-android14-11-maybe-dirty #1
```

**这说明什么**：内核**完整跑完了内核态的初始化** —— 设备树解析、内存管理、
SMP 启动、驱动 probe（串口 pl011 已工作）、VFS 初始化 —— 然后因为**没有根文件系统**
而 panic。这正是 `RAMDISK_SZ=0` 的必然结果。

**对 patch 的意义**：这不是「镜像有问题」，恰恰相反 —— 它证明 patch **没有破坏
内核启动路径**。如果补丁踩坏了调度器/内存管理/中断，内核会在**更早**的地方就崩，
到不了 `mount_block_root`。

### 4.3 串口日志对比方法（归一化 + 内容集合）

直接 `diff` 两次启动的串口日志**永远不相等**，因为每次启动必然变化：

| 噪声 | 例子 | 归一化为 |
|---|---|---|
| 内核单调时间戳 | `[    0.554621]` | `[T]` |
| `[cpu:pid:comm]` 前缀 + 行内 PID | `[0:46:cryptomgr_probe] … (46)` | `[cpu:pid:comm]` / `(<pid>)` |
| audit 时钟 | `audit(0.212:1)` | `audit(T)` |
| RTC 墙钟 | `setting system clock to 2026-11-11T10:38:50 UTC (1794393530)` | `<ISO> UTC (<epoch>)` |
| 栈深采样 | `used greatest stack depth: 15056 bytes left` | `<N> bytes left` |
| **KASLR 偏移** | `Kernel Offset: 0x2179800000` | `<KASLR>` |

归一化后再做**两种独立对比**：

1. **顺序敏感**（`identical_after_normalisation`）：逐行比。异步 probe（cryptomgr、
   workqueue）落点不确定，同一内核两次启动也会有 2~3 行换序。
2. **内容集合**（`same_line_multiset`）：按行计数比。**这是更强的结论** ——
   「同样 290 行、一条不多一条不少」等价于「没有代码路径发生改变」。

本次结果：**顺序不同 2 行、内容集合完全相同**。逐行不同不等于有问题，
但少了/多了某一行就是真信号 —— 后者由 `lines_only_in_orig` /
`lines_only_in_patched` 单独列出，且有负样本 `NEG-BOOT-multiset-missing` 保证它不会被吞掉。

### 4.3 为什么这是「中等强度」证据

- 强：内核真的执行了 33 MB 补丁镜像的代码，跑了几十万条指令，没崩。
- 弱：qemu 的 `-M virt` 不是魅族 21 的硬件；真机的 GPIO/I2C/display 栈**根本没被**
  qemu 触发，所以「驱动是否正常」在 C 层**无法回答**（这正是 §3 静态做的原因）。
- 弱：没有 ramdisk ⇒ 从未进入用户态 ⇒ Android 框架、init、Zygisk、`apd` 全未执行。

## 5. qemu 通过 ≠ 真机可开机（诚实边界）

**C 层能证明的**：patch 后内核镜像结构完好、能被真实 CPU 模型执行、内核态初始化
路径未被破坏、与原厂行为无差异。

**C 层不能证明的**（真机必须单独验证）：

1. **驱动是否正常** —— qemu 只驱动了 pl011 串口和 virtio，魅族的触摸/摄像头/wifi/
   显示/充电全未触及。B 层的静态检查是当前唯一的预防手段。
2. **能否进入用户态** —— 取决于真机 ramdisk（本样本 `RAMDISK_SZ=0`，ramdisk 在
   `init_boot.img` 里，本次未合并）。
3. **是否触发 AVB 校验失败** —— 真机有 bootloader 校验，qemu 没有。
4. **温度/功耗/时序** —— 完全不在模拟范围内。

**真机验证清单**（按顺序，任一失败即回滚）：

```bash
# 1. 刷入前确认产物
sha256sum new-boot.img            # 与 CI 产物比对
fastboot getvar current-slot
# 2. 只刷 boot，保留 vbmeta 不动
fastboot flash boot new-boot.img
fastboot reboot
# 3. 起来后立刻看内核有没有报错
adb shell dmesg | grep -iE 'panic|BUG|Oops|Call trace' | head
adb shell 'cat /proc/uptime'      # 能读到且在涨 = 内核活着
# 4. 逐项验证驱动（对照原厂镜像刷回时的表现）
adb shell 'ls /sys/class/drm/card0'        # 显示
adb shell 'dumpsys battery | head -5'      # 充电
adb shell 'cmd wifi status'                # wifi
adb shell 'ls /dev/input/event*'           # 触摸
adb shell 'dumpsys media.camera | head'    # 摄像头
# 5. 失效线
fastboot flash boot stock-boot.img         # 任一异常立即回滚
```

### 7.1 开发过程中被负样本抓到的缺陷（5 个，全部"曾看起来正确"）

按发现顺序，这是本体系可信度的真实来源：

| # | 缺陷 | 怎么被发现的 |
|---|---|---|
| 1 | **PA-3 是空断言**：用"周围 4KB 代码密度"判定，对每一处（含密钥数据）都返回 0.99~1.00，任何阈值都是恒 PASS/恒 FAIL | 跑真实内核时发现全部判 code，怀疑没有区分度 |
| 2 | **L3 误判为 True**：panic 调用栈里有 `kernel_init` 字样，而 marker 表里恰好有它 → 把「内核线程」当成「用户态 init」 | 人工查看串口日志，发现根本没进用户态 |
