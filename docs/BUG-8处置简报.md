## 1. 问题现象

- 计划条目 `pl_8780230ebd752cfc` 的**绑定指针固化在已被人类归档的任务 `t_9de953beb3c7bbf8` 上**。

## 3. 根因推断

- **直接根因**：任务 `t_9de953beb3c7bbf8` 归档后，计划条目 `pl_8780230ebd752cfc` 的 `bound_task` 指针未随之迁移或解除，固化指向一个「无执行权持有者」的死引用。
- **框架层缺陷**：ai-buddy 计划模块**缺少「条目解绑 / 重绑」机制**：
  1. 任务归档时，框架不会自动迁移或清空其绑定条目的指针；
  2. 成员新建承接任务并在 create_conversation 中声明绑定条目时，**不能替换**条目上已有的旧指针；
  3. 权限模型据此判定「绑定任务无持有者 → 仅人类可改」，把成员完全挡在门外。
- **佐证**：同批次归档还产生了同类问题——`pl_55b89e1161f02d61`（系统守护，绑定死任务 `t_e547ed06d717a26b`）与 `pl_c86514ad3488e53f`（内核修补，绑定空缺）均需 leader 用 `create_conversation + handoff` 绕行或人工处理。BUG-8 是该缺陷族中最典型的一例（承接任务已存在却无法挂接）。

## 4. 给审查员的修复建议

1. **绑定指针随归档自动迁移/解除**：任务被归档时，若其上挂有计划条目，应（a）触发绑定迁移流程，或（b）至少将条目指针置空并解锁条目，回到「待指派/可绑定」状态。
2. **允许条目解绑/重绑**：为持有承接任务执行权的成员提供「条目重绑」能力（如 `rebind_plan_item(plan_item_id, new_task_id)`），校验规则 = 新任务持有者即申请人即可。
3. **归档前置校验**：归档任务时若其绑定条目仍有未完成状态（非 done），给出警告或要求先移交执行权。
4. **报错信息可操作性**：当前报错只说「only a human may change it」，建议附上「可重绑到的候选任务」或明确指引调用 rebind 接口，减少人工介入。
