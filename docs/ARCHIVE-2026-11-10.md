## 2. 本次会话完成的三条主线

### 2.1 真机首跑 Bug 三连修

| Bug | 根因 | 修法 | 教训 |
|---|---|---|---|
| 修补"成功但无产物" | 引擎成功分支无条件 `remove_all(--workdir)`，客户端 `--out` 恰在 workdir 内 → 产物被删却返回 0 | 显式传 `--workdir` 一律不删；默认 `<out>.work` 才回收 | 契约必须写明"谁拥有目录生命周期" |
| 密钥 ABI 全链错配 | App 48 / 引擎要 48 / 内核存 47+NUL / 提权须 47，四处口径不一 | 全链统一 47；引擎 `embed_key_bytes()` 收口 `key[0:47]+NUL`；`escalation_token()` 改 `Result` 钉死长度 | **最隐蔽的断链**：现象与"AP 未部署"完全一样 |
| 旧路径 `superkey` | app 侧 3 处写错（应为 `/data/adb/sproot/key`） | 全部更正 | 路径必须单一常量来源 |

**修 workdir 时我（Lead）也犯了一个错**：写的"双重保险②"`out_inside_workdir` 在 `workdir == default` 时**恒为 false**，是**不可达死代码 / 安全剧场**。被 engine-dev 指出后重写为「解析期标记 `workdir_from_user` + 判定所有权来源而非值」。
→ 教训：**注释宣称的保护必须在决策路径上真实参与**，否则比没有更危险。

### 2.3 C′ rc 虚拟化（**本次最大价值项**）

**发现**：APatch 不改 init_boot 的秘密不是"启动器"，而是 hook `openat` 把 init 要读的 rc 换成 `/dev/user_init.rc`（原 rc 内容 + 追加段）。

**我们的实现**（clean-room，`engine/src/patch_rc_virtualize.cpp`）：
- hook `__arm64_sys_openat`，双层过滤 `uid==0 + O_RDONLY`
- 读原 rc → 写 `/dev/user_init.rc`（原文+模板）→ **原地覆写用户 path 串**（28/34 B > 18 B，不改栈指针，省掉 `pt_regs->sp` 推导与 compat 分支）
- 不需要 `replaced` 标志（幂等重写）
- **洞扫描零硬编码** + 三重断言（在 `.text` 内 / 逐字节 0 / ≥2048 B），`report.launcher.caves[]` 输出实测洞清单
- **默认 `--launcher off`，off 时产物与旧引擎逐字节相同**（`git worktree` 编译旧 HEAD 对照 `cmp` 验证）
- 真机 6.1 实测：洞 `0xf937d4`(2092 B)，blob 836 B，13 处 BL 全命中符号，组数 15/15

**价值**：`init_boot` 修补整条链（unpack / repack / T-12 / AVB-1/2/3）**可以退役**。

## 3. 「排除修改」全链路（生态集成）

### 3.1 APatch 的真实实现（源码级）
| 部件 | 位置 | 内容 |
|---|---|---|
| 存储 | `KernelPatch/.../sucompat.c:511` | `set_ap_mod_exclude(uid, exclude)` → kstorage 存 per-uid 一个 int（内存态，不落盘） |
| 写入 | `apd/src/supercall.rs:98` | `sc_set_ap_mod_exclude` 经 supercall 发命令，`supercmd.c` 派发 |
| **消费** | `supercall.c:421` | `if (get_ap_mod_exclude(uid)) return;` ← **在文件重定向入口按 uid 短路** |

**本质**：APatch 的模块机制是**内核层 supercall 文件访问重定向**（类似 magic mount 但在内核里），"排除修改"就是在重定向入口按 uid 短路。
**我们 apd 的 `package.rs:32` header `pkg,exclude,allow,uid,to_uid,sctx` 与 APatch 一字不差** —— 同一血统，`exclude` 字段一直存在但从未实现语义。

### 3.2 我们的落地方案（借生态，不重写模块系统）

```
① C′ rc 虚拟化 → init 读到我们的 rc
② rc 里 on post-fs-data: exec -- /data/adb/apd post-fs-data   （exec 是 init 阻塞原语）
③ apd PostFsData 子命令 → exec_stage_script("post-fs-data") 遍历所有模块
④ NeoZygisk 的 post-fs-data.sh 启动 zygiskd（此时仍早于 zygote）
   Mountify 的 post-fs-data.sh 建立 overlay 挂载
⑤ zygote fork 时 NeoZygisk 注入 → 读 /data/adb/ap/package_config 的 exclude
⑥ exclude==1 的 uid → unmount source=="APatch" 的挂载 → 干净 namespace
```

### 3.3 关键对接事实（全部实测）

| 事实 | 值 |
|---|---|
| NeoZygisk 读配置 | `/data/adb/ap/package_config`，CSV `pkg,exclude,allow,uid,to_uid,sctx` |
| NeoZygisk 认 root 方案 | 执行 `apd -V`，取 `split_whitespace().nth(1)` 转 i32，要求 **≥ 10762** |
| `minAPatchVersion` | **10762**（`NeoZygisk/build.gradle.kts:21`） |
| 卸载判定 | `info.source == "APatch"`（`unmount.cpp:136`） |
| Mountify 开关 | `config.sh` 的 `MOUNT_DEVICE_NAME`，**必须从 `"overlay"` 改成 `"APatch"`** |
| Mountify 硬要求 | **`CONFIG_OVERLAY_FS=y`** |

## 4. 代码级关键事实（**接手必读，勿再踩**）

### 4.1 SELinux 域约束
```
untrusted_app 只能 exec nativeLibraryDir/libapd.so
/data/adb/apd 只能作为 root-exec 的「目标命令参数」，绝不能当引导器
```
- `ApdClient.apdBootstrap()` = 引导器（永远 `nativeLibraryDir`）
- `ApdClient.deployedApd()` = 部署目标（只作参数）
- **历史 bug**：曾用 `if (/data/adb/apd 存在) 用它 else 用 nativeLibraryDir` → **部署后反而全线不能提权**（"越装越坏"）

### 4.2 PATH 坑（**P0 待修**）
```rust
BINARY_DIR  = "/data/adb/ap/bin/"    // ← 进模块脚本 PATH 的是这个
DAEMON_PATH = "/data/adb/apd"        // ← apd 实际在这里
```
→ NeoZygisk 的 `Command::new("apd")` **找不到** → 判定 `RootImpl::None` → **Zygisk 链静默失效**，且失败是 `debug!` 级日志，真机看不见。
**修法**：①`/data/adb/ap/bin/apd` 建符号链接 ②PATH 加 `/data/adb` ③`selftest` 加 `apd_in_path` 检查。

### 4.3 zygiskd 启动时机（**已修**）
NeoZygisk 必须在 **zygote 之前**注入。原模板只在 `boot_completed` 启 daemon → **必然错过**。
已加（`4f9c5e9`）：`on post-fs-data` 段 `exec -- /data/adb/apd post-fs-data`。
**风险**：`apd post-fs-data` 卡住会**拖慢开机**（不是崩溃）→ **apd 侧需该阶段硬超时（待办）**。

### 4.4 密钥 ABI（铁律）
```
App 生成 / 存储 / 提权串 / daemon 文件 = 47 字符，无 NUL
调引擎时补成 48（引擎 valid_key 硬要求 size==48，内部丢弃第 48 位）
内核内嵌 = key[0:47] + NUL（恰 48 字节，第 48 字节恒 0）
```
- 「重新生成」必须二次确认并警告"已修补镜像内嵌旧密钥，需重新修补刷入"
- 已删除"历史 48 位兼容机制"（人类明确要求：一机一份固定不变）

### 4.5 密钥读取缓存
`SecretStore` 有进程内缓存 —— 曾因无缓存，一次启动读 5 次 Keystore 并打 5 条 warn。

### 4.6 「已安装」判定
```kotlin
installed = (status == ACTIVE)
```
且 ACTIVE **只能由真实探测 `selftest stage=daemon_ready`** 产生（`InstallState.markActiveDetected`）。
授权操作**绝不**影响安装状态（人类反馈："设了 root 权限就显示已安装" 是错的）。
`PATCHED_PENDING_FLASH` / `FLASHED_PENDING_REBOOT` / `UNPATCHED` / `ERROR` 一律显示"未安装"。

### 4.7 启动路径必须异步
- `DaemonBootstrap` 全部流程移出主线程（主线程守卫：误调即记错误返回 FAILED）
- 探测超时 **60s → 5s**（只探 daemon 在不在，不该等一分钟）
- 崩溃兜底 `CrashHandler` → `Downloads/SPRoot/crash-*.txt`（含机型/ABI/完整堆栈/最近 200 行日志）
- **首开闪退的推定根因**：主线程被同步 root-exec 阻塞 → ANR → 被杀

### 4.8 init_boot 的语义
**`init_boot` 分区里没有 kernel**，SP 的修补是纯内核字节补丁 → **init_boot 无可修补之物**。
- `boot.img` = **修补内核**（获得提权能力）
- `init_boot.img` = **注入自启脚本**（让 daemon 开机自启）
C′ 完成后，第二项可整体退役。

### 4.9 AVB 与解锁（刷机前提）
| 状态 | 结果 |
|---|---|
| **bootloader 已解锁** | ✅ 能启动（AVB 不阻止，只把 `verifiedbootstate` 置 orange） |
| **未解锁** | ❌ 必然无法开机 |

`fastboot flash boot` / `flash init_boot` 是标准做法（Magisk / KSU 都只刷 boot）→ **不需要刷 vbmeta**。
`--disable-verification` 才是清数据元凶（它改 vbmeta 本身、破坏验证链）。**永不使用**。

## 5. 已明确「不做」的路线

| 路线 | 结论 | 理由 |
|---|---|---|
| **B** 重写模块系统 | ❌ 不做 | 等于重写整套挂载（overlay/bind/白名单/原子性） |
| **D** 动态遍历 vfsmount | ⚠️ **降级备选** | 生态已解决（Mountify 预留 `MOUNT_DEVICE_NAME`）。1.2 KB + setresuid hook + 反汇编偏移，成本远高于用现成组件 |
| **G** 轻量 VFS 旁路 | ❌ 不做 | 需 hook 10+ syscall，等于重做 VFS 路径解析 |
| **E** 自研 Zygote 注入 | ❌ 不做 | 重造 Zygisk 提供者 |
| **C** init hook + usermodehelper | ❌ 不做 | init exec 早于 `/data` 挂载，UMH 必失败；失败 = 开不了机 |
| **Zygisk Next** | ❌ 不能内置 | 无 LICENSE |

**D 路线的分析价值已保留**（`docs/NEW-DOC-02 §10`）：反汇编实证 `iterate_mounts` 有 kCFI 检查（`brk #0x8228`）、`path_umount` 自取 `namespace_sem` 写锁会死锁、`dget` 不在 kallsyms、结构体偏移清单（`current->nsproxy=0x888`、`mount=mnt-0x20`、`&mnt_list=vfsmount+0x90` 等）、`setresuid` 才有 CAP_SYS_ADMIN 而 execve 已降权。
→ 若生态方案失效，这是现成路线图。
