## 1. 最痛的教训：avb_untouched 的两次「假修复」

这个案例值得单独记录，因为它**一次失败、一次救回**，正好演示了什么算真修。

### 1.1 原始形态（结构性永远 PASS）

```rust
// deploy.rs
avb: "vbmeta_untouched".to_string(),      // 写一个常量
// selftest.rs
state.avb == "vbmeta_untouched"           // 再读回来跟同一常量比 → 恒真
```

与 `docs/HANDOFF-2026-11-08.md:153-155` 记录的 AVB-3 空断言**同型**。

### 1.2 第一次修复：方向对，但在真机上永远不可达

改成真实读取分区尾 64B 找 `AVBf` 魔数 → 大端解 `vbmeta_offset`/`vbmeta_size` → 算双 sha256。方向正确，但有个物理缺陷：

```rust
let len = file.metadata().len();   // ← 块设备的 st_size 恒为 0
if len < AVB_FOOTER_SIZE { return Unobservable; }
```

**实测**（WSL）：

```
/dev/sda     isblk=True  st_size=0   SEEK_END=758038528
/dev/loop0   isblk=True  st_size=0   SEEK_END=0
```

→ 所有真机都命中 `partition too small (0 B)` 早退 → `avb_ok` **任何设备上都不可达**。

**为什么负样本没抓到**：六个 AVB 单测全部用 `synth_partition()` 写**普通文件**。测试环境与生产环境不同构 —— 这正是「负样本只在同构环境里才有意义」的注脚。

### 1.3 第二次修复：让它能在真设备上成立

```rust
fn real_len(file: &mut fs::File) -> io::Result<u64> {
    file.seek(SeekFrom::End(0))    // 普通文件与块设备同一路径都正确
}
```

并用 `losetup` 挂**真 loop 块设备**做测试，且把 bug 的物理事实钉进断言：

```rust
assert_eq!(meta.len(), 0, "precondition: block devices report st_size == 0");
assert_eq!(observed.partition_bytes, 8388608);
```

负样本（把 `real_len` 改回 `metadata().len()`）：

```
test avb_probe_works_on_a_real_block_device ... FAILED
panicked: block device size must come from SEEK_END, not st_size (got 0)
  left: 0   right: 8388608
```

**结论**：一个断言「改了方向」不等于「修好了」。判断标准只有一个 —— **它在真实形态上能不能变红**。

## 2. 假门禁专项：功能删了为什么还不红

| 门禁 | 旧写法 | 实测绕过方式 | 新判据 |
|---|---|---|---|
| `apd.yml` 能力 | `grep -aq undeploy` | 从 `cli.rs` 删 `Undeploy` 后仍 PASS（命中的是 selftest 的 `"undeployed"` 状态串） | CLI about 契约 + 代号组全齐 + 过期字面量禁复活 |
| `apk.yml` rc 模板 | `grep -q oneshot` | 删掉 service 块内 `oneshot`/`disabled`/`override`/`class` 四行、注释保留 → 四条 grep 全 PASS | 剥离注释 + 按 `service sproot-apd` 块解析（17 条断言） |
| `release.yml` 许可 | `grep -aq resetprop` | 干净构建（`--no-default-features`）产物里也有 `resetprop` **7 次**（存根错误文案）→ 干净构建被判成含 UNKNOWN | `grep __system_properties_init`（实测干净=0 / default=2） |
| `ci-static.yml` 产物校验 | 只跑 `verify_patch.py --help` | 400+ 行 V/BI/RB 断言**在 CI 里一条没跑过** | `--self-test` 合成夹具 + 覆盖度双向闸门 |

### 2.1 capability 子串匹配：这个取舍是对的，不再改

`check_apd_capabilities.py` 的 `code_present()` 用朴素子串判定。曾两次尝试更严格的边界解析，**都在正确产物上假红**：

1. Rust release 把相邻字面量拼进同一字符串池：`avb_no_footer` 与 `avb_ok` 实际存成 `configavb_no_footeravb_ok`（无 NUL 分隔）。
2. 按已知码切分同样不可靠：池的相邻关系由链接顺序决定，逐次构建都在变。

**判定**：保留子串匹配。理由是威胁模型 —— 本项目真实失效模式是**功能被删除**（删 → 子串必消失 → 变红），而非"被更长标识符冒充"。当前 6 个坏样本（含 `subcommand-undeploy-removed`、`avb-tri-state-collapsed`、`legacy-sentinel-revived`）全部实测变红。

> 会误报的门禁比没有更糟 —— `vbmeta_untouched` 就是这么被无视掉的。

## 3. 密钥 ABI：一个反直觉的坑

| 位置 | 正确形态 | 错误后果 |
|---|---|---|
| App 生成/存储/root-exec/daemon 文件 | **47 字符纯文本，无 NUL** | — |
| 调引擎 | 补到 48（引擎只用前 47 位） | — |
| 内核内嵌 | `key[0:47] + NUL`（恰 48 字节） | — |

**反直觉点**：给 AP 侧密钥文件加 NUL 会**反而搞坏提权** —— `read_to_string` 带回 `\0`，转 `CString` 时 `CString::new` 因内部 NUL 直接失败。

另有 Skroot-Next 体系的「48 字节无 NUL、按实际长度比较」ABI，与本项目**不可混用**；引擎侧已对错体系密钥**显式硬拒**（`skroot_patch_main.cpp` 的 `--key-abi` 校验）。

冻结契约 `phase2_skroot_ap_call_contract_v1.1.md:183` 原先写「48 字符原文」，本轮已按代码事实改为 47 并附 E7 勘误 + 附件 B。

### 4.3.1 真机日志暴露的两个 bug（2026-11-11，vivo V2344A / Android 15）

用户提供的两份真机文件是本轮**唯一来自真实设备**的证据：

```
crash-20261111-065108-576.txt:
  NullPointerException: Can't toast on a thread that has not called Looper.prepare()
    at Toast.<init> → PatchPageKt.LogExportLine$lambda$0$0$0(PatchPage.kt:502)

sproot-log-20261111-065108.txt:
  ERROR [Pipeline] 修补失败：修补异常中断 阶段=校验产物 进度=92%
  java.lang.IllegalArgumentException: Root 密钥必须是 47 字符…实际长度=48
    at SecretStore$Companion.kernelKeyOf(SecretStore.kt:89)
    at PatchPipeline.execute(PatchPipeline.kt:833)
```

**第二个尤其值得记录，因为它是上一轮修复引发的回归**：本轮给 engine 补 `report.root_key` 字段后，客户端那句
`PatchEngine.lastRootKey()?.let { SecretStore.kernelKeyOf(it) }`
从「永远走 `?: key` 兜底」变成「真的拿到 48 字符」。产物其实**已经成功导出**
（`Download/SPRoot/boot_patched_20261111-065057.img`，100663296 B，AVB-1/2/3 全过），

## 7. 方法论沉淀（下次别再踩）

1. **「改成实测」不等于「修好」**：必须问「这个实测在真实形态上可达成吗」（AVB 的 st_size 教训）。
2. **负样本只在同构环境里有效**：用普通文件测块设备路径 = 没测。
3. **会误报的门禁比没有更糟**：它会训练人忽略它（`vbmeta_untouched` 的死亡方式）。宁可保留一个有明确威胁模型覆盖的弱判据，也不要一个爱喊狼来了的强判据。
4. **先写会红的负样本，再写断言**：本轮每个新断言都配了变异测试，全部贴了真实输出。
5. **「无法判定」不是终点**：14 vs 15 无法当场裁决，正确解法是让系统自己输出可对账的推导过程，而不是把疑问留在文档里。
6. **破坏性工具要谨慎**：本轮一度用 PowerShell `Set-Content -NoNewline` 重写含中文的 Python 文件，导致字符串被合并、语法崩坏，只能 `git checkout` 回退。**改代码用 read/edit，不要用 Set-Content 整文件重写**。
